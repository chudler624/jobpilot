# Architecture Decisions

## ADR-001 — Database: Supabase PostgreSQL
**Decision:** Use Supabase for database, auth, and storage.
**Reason:** Free tier is generous (500MB DB, 1GB storage, 5GB egress, 50k MAU), real PostgreSQL under the hood, and auth/storage come bundled instead of being built by hand.

## ADR-002 — Hosting: Vercel
**Decision:** Deploy on Vercel.
**Reason:** Native, effectively zero-config Next.js deployment; free Hobby tier is enough for a personal prototype; GitHub → Vercel gives automatic deploys on every commit.

## ADR-003 — AI Provider: Gemini (behind an abstraction layer)
**Decision:** Start with Gemini (e.g., 2.5 Flash) via a swappable provider layer.
**Reason:** Free tier is sufficient for single-user testing. The provider layer means we can swap in Claude, DeepSeek, or a different Gemini model later without rewriting business logic. Do not assume any specific Gemini model/version stays current — check pricing/availability when wiring this up, since Google's lineup changes.
**Note:** Free-tier Gemini terms may allow Google to use prompts/responses to improve their products; paid tier does not. Acceptable for a private single-user prototype containing only the user's own data — revisit before any other person's resume/data enters the system.

## ADR-004 — Frontend: Next.js + TypeScript
**Decision:** Single Next.js application (frontend + API routes), not a separate frontend/backend split.
**Reason:** One codebase, works well with Claude Code, avoids premature complexity.

## ADR-005 — Browser automation / application autofill: Deferred to Phase 8
**Decision:** Do not build browser automation into the core app. When built, it will be a separate browser extension, not part of the Next.js codebase.
**Reason:** Not required to validate the core product (Career Profile → Job Analysis → Match → Tailored Resume → Tracking). Keeps the core app's architecture clean.

## ADR-006 — No automated application submission
**Decision:** The app prepares and assists; a human always reviews and submits.
**Reason:** Safer, avoids fragile per-site scraping/automation, and avoids submitting incorrect or ungenuine answers on the user's behalf.

## ADR-007 — Multi-user-capable schema, single-user product for now
**Decision:** Design tables with a `user_id` / ownership model from day one, but do not build any team/org/admin/billing UI until Phase 10.
**Reason:** Avoids a rewrite later if this becomes a SaaS, without spending time now on features that don't matter for a single user.

## ADR-008 — Job descriptions and scraped content are untrusted input
**Decision:** Any externally sourced text (job postings, fetched pages) is treated strictly as data to parse, never as instructions.
**Reason:** Prompt-injection risk — a job posting or webpage could contain text designed to manipulate the AI's behavior.

## ADR-009 — No LinkedIn/Indeed scraping dependency
**Decision:** Primary job discovery relies on company career pages and ATS platforms (Greenhouse, Lever, Ashby, Workday, etc.) or manual paste-in, not scraping LinkedIn or Indeed directly.
**Reason:** Both platforms prohibit automated scraping in their terms; building a dependency on it makes the product fragile and puts the account at risk.

## ADR-010 — Resume import requires human review before persisting
**Decision:** AI-extracted Career Profile data from an uploaded resume (Phase 1.5) is never auto-saved. It's shown in an editable review screen (include/exclude, edit any field) and only written to the database after explicit user confirmation.
**Reason:** Every other AI flow in the app has an automated truth-check available — a zod schema validates shape, and where the AI cites an existing row (Match Engine, Resume Engine), code independently verifies that citation against the real profile. Resume import has no such net: the AI is *creating* new claims about the user's history, not citing existing ones, so there's nothing pre-existing to verify against. Human review is the truth-check for this specific flow, not a UX nicety.

## ADR-011 — Resume file text extraction: unpdf + mammoth
**Decision:** Use `unpdf` for PDF text extraction and `mammoth` for DOCX text extraction (reading existing files), for the Phase 1.5 resume-import feature.
**Reason:** `unpdf` is built for serverless/edge runtimes (matches Vercel), verified actively maintained (checked npm registry directly rather than assumed). `mammoth` is the established library for converting existing `.docx` content to text. Both are distinct from `docx` (Phase 4's planned generation library), which can write new `.docx` files but cannot usefully read arbitrary existing ones back out.

## ADR-012 — Truth Guard's "finalize" gates a human-confirmation milestone, not download access
**Decision:** A resume version's `draft` → `finalized` transition (Phase 5) requires every `resume_sections` row to be `user_verified`, but `status` never restricts the existing Download action — a draft resume downloads exactly as it did before Phase 5.
**Reason:** Phase 4's citation-fabrication check (DB foreign keys + `findFabricatedResumeCitation`) already makes a fabricated claim impossible to persist, unconditionally — so nothing about download itself is unsafe pre-finalization. Gating download on finalize status would reintroduce the same kind of hard block already rejected once during Phase 4 live testing ("it should just produce a warning, but not completely refuse to do it"). Finalize is instead an opt-in trust milestone the user reaches after reviewing each claim's evidence on the new `/resume/[versionId]/review` page — its main effect today is the Draft/Finalized badge; it's also the flag a future Application Tracker phase will likely want to read (e.g. "only finalized resumes can be attached to an application"), but that integration is explicitly not built now.
**Note:** Confidence ("well-evidenced" vs. "thin") is computed on read from the cited row's live `evidence_strength`/`verified` data via a shared `isCitationWellEvidenced` helper (`lib/match/score.ts`), reused as-is from Match Engine's `resume_representation_score` — not stored, so it can't go stale if the Career Profile changes after generation.

## ADR-013 — Application Tracker: no resume-finalization constraint, job deletion restricted instead of cascading
**Decision (Phase 6):** `applications.resume_version_id` may reference a resume version in any state (`draft` or `finalized`) — no DB check or app-level validation requires `finalized`. Separately, `applications.job_id` is `on delete restrict` (the only cascade-style FK in this schema that isn't `cascade` or `set null`).
**Reason (resume constraint):** Consistent with ADR-012 — finalize is an opt-in trust milestone, not access control, and that principle wasn't a one-off (it was also the explicit, repeated conclusion during Phase 4 live testing: "should just produce a warning, but not completely refuse to do it"). A hard constraint here would also break a legitimate case: backfilling an application submitted before this feature existed, using a resume never formally checked off. Instead, the application detail page shows a non-blocking warning when the attached resume is still Draft, linking to its review page — the same warning-banner pattern already used elsewhere, not new mechanism.
**Reason (job deletion):** Unlike `resume_versions.job_id` and `job_scores.job_id`, which cascade because their data is fully regeneratable from the job, an `applications` row is irreplaceable personal history (status timeline, contacts, interview notes) — it must never be silently destroyed by deleting a stale job posting. This made `deleteJob` able to fail in a real, common way (not just a rare bug), so it was converted from throw-on-error to the standard `ActionState` pattern (catching the Postgres FK-violation code and returning a clear message) instead of crashing to Next's generic error page.
**Also decided:** `applications.match_score_at_creation` is a one-time numeric snapshot of `job_scores.overall_score`, not a live join or FK — `job_scores.job_id` is unique and re-analysis deletes-then-inserts the row (no history), so a snapshot is the only way an application's recorded match score survives a later re-analysis or job deletion, which Phase 9's planned "match score: interviewed vs. not" analytics will need. A `unique (user_id, job_id)` constraint on `applications` keeps one application per job, matching the "Track this application" entry point on the job detail page.

## ADR-014 — Job Discovery: Greenhouse only, filters split pre/post-extraction, no queue
**Decision (Phase 7):** The first (and, for now, only) discovery source is Greenhouse's public Job Board API (`boards-api.greenhouse.io`) — the user adds "watched companies" by their Greenhouse board token, and a fetch pulls that company's full open-jobs list in one call. Lever, Ashby, and Workday are explicitly deferred, not built.
**Reason:** Greenhouse's API is documented for external consumption (companies use it to embed their own listings elsewhere) — this is categorically different from scraping LinkedIn/Indeed (ADR-009), and it's free with no key/account required, keeping this a zero-new-account-dependency feature. A third-party aggregator API was considered and rejected: it would add a paid/keyed external dependency and real risk of sourcing from LinkedIn/Indeed under the hood, violating ADR-009's spirit even without directly scraping them.
**Filter-mapping limitation, stated explicitly:** Greenhouse's list endpoint has no search/salary/experience query parameters — "search" in this phase means "pick which companies to pull from," not a query against an external index. Role/location/exclusion filters are applied **pre-extraction** (cheap, narrows what's inserted before any AI call runs); salary/experience filters can only be applied **post-extraction** (over the already-processed set), since Greenhouse's list JSON doesn't structure either field. Experience filtering reuses `parseMinYears` from Match Engine's scoring code rather than a second parser.
**Dedup:** `source_url` alone is the dedup key for discovery-sourced jobs (Greenhouse always provides a real `absolute_url` per posting — no fuzzy company+title+date fallback was needed). Enforced via a partial unique index (`jobs.source_url` stays nullable for paste-text entries). Duplicates are skipped, never used to overwrite an existing row — the whole point of the stored `raw_description` snapshot is that it's point-in-time (ADR from Phase 2), and silently overwriting it on rediscovery would break that.
**Scoring:** discovery reuses `analyzeMatch` exactly as it already exists — no second scoring mechanism. Extraction and scoring run synchronously per job, batched only via sequential client-side calls (`ProcessJobButton`) rather than a queue or background worker — ruled out per CLAUDE.md's "no Redis/queue unless forced," and each call stays within its own bounded server-action invocation regardless of batch size.
**Verified live before building the UI around it:** both the API response shape and a real formatting quirk — several Greenhouse boards (confirmed on GitLab's and Stripe's) return the `content` field HTML-entity-encoded on top of real HTML, so a single strip pass leaves literal `&lt;div&gt;`-style text behind. `lib/jobs/greenhouse.ts` re-strips (bounded to 3 passes) whenever the result still looks like markup.

## ADR-015 — Application Assistant: extension auths directly via Supabase + RLS, no new API surface
**Decision (Phase 8):** The browser extension (`extension/`, a separate package in this same repo, Vite + `@crxjs/vite-plugin`, Manifest V3) embeds the Supabase JS client and authenticates as the user directly — no new `app/api/...` route surface, no personal-access-token system. Every table read goes through the exact same RLS policies every other client of this database already uses.
**Reason:** A token-based API surface would mean designing and independently verifying a second authorization mechanism whose only job is to re-derive a guarantee RLS already provides. Reusing RLS directly means the constraint "no new access path that bypasses per-user data isolation" is satisfied by construction, not by a new thing that could be gotten wrong. The Supabase publishable key shipped in the extension is the same key the deployed web app already ships in its own browser bundle — not a new exposure.
**Sign-in mechanism — deviates from the planning doc, decided during build:** the plan proposed `chrome.identity.launchWebAuthFlow` (redirect-based). Implemented instead: a 6-digit email-OTP code typed directly into the popup (`supabase.auth.signInWithOtp` → `verifyOtp`), the same underlying mechanism as the main app's magic-link sign-in. This needs zero Supabase redirect-URL configuration and no `identity` permission at all — simpler and more reliable inside an extension popup than a redirect flow, found while implementing rather than assumed upfront.
**Access scope:** read-only. `experiences`, `accomplishments`, `skills`, `projects`, `evidence`, `profiles` — no write path in this phase (not even logging that a page was visited).
**Permissions, kept minimal:** `activeTab`, `scripting`, `storage` — no persistent `content_scripts` manifest entry, no broad `host_permissions` over arbitrary job sites. The content script is bundled to a stable unhashed path (`assets/content.js`, forced via a dedicated Rollup `entryFileNames` rule — crxjs only auto-bundles scripts declared in the manifest, and declaring it there would mean auto-injecting on every page) and injected on-demand via `chrome.scripting.executeScript`, triggered only by the user clicking "Detect fields" in the popup. The one necessary `host_permissions` entry is the Supabase project's own API domain, for the background worker's fetches.
**Two schema gaps found while wiring answer derivation, fixed rather than worked around:** work authorization status and phone number weren't captured anywhere in the Career Profile schema. Added `profiles.work_authorization_status`, `profiles.requires_sponsorship`, `profiles.phone` (small, justified additions — the same reasoning as every other schema addition made when a real need surfaces) plus corresponding Settings-page fields.
**Answer-generation scope:** structured/factual fields only (name, email, phone, years of experience, skill yes/no, work authorization) — no AI-generated prose answers. Years of experience is computed via `computeExperienceYears` (reused verbatim from Match Engine, not reimplemented), summed only over `experiences` rows whose `technologies` array tags the relevant skill; if a skill is recorded but never tagged on any experience, the answer is "0 years tagged" rather than either fabricating a number or treating it as unknown — the same have-it-but-not-represented distinction Truth Guard already established for resumes.
**No-AI in field interpretation:** detection is pure regex/keyword matching against DOM label text — no page content is ever sent to an AI provider in this phase, so ADR-008's prompt-injection concern doesn't apply by construction (there's no AI call in the path for it to inject into).
**No-auto-submit, enforced structurally:** the content script's message protocol exposes exactly two actions, `DETECT_FIELDS` and `FILL_FIELD` — there is no `SUBMIT` action anywhere in the codebase, and fill only ever sets a field's value via a user-triggered click. This mirrors how other truth-sensitive flows in this app (e.g. `commitImport`) are enforced by the absence of a code path, not a runtime toggle.
**Known, stated limitation:** radio buttons and checkboxes are skipped entirely by field detection — many yes/no questions (sponsorship, work authorization, skill checks) are rendered as radio groups or custom toggles rather than a plain `<select>`, and reliably picking the correct option within a group is meaningfully harder than filling one field. Not solved in this phase; documented in `extension/README.md` rather than silently glossed over.
**Verification note:** field-categorization and answer-derivation logic were verified with throwaway Node scripts (10/10 and cross-checked-against-Match-Engine test cases respectively) before being wired into the browser-only layers. The extension's full build (`npm run build`) was run and produces a structurally valid MV3 bundle. Sign-in, live field detection, and fill on a real application page could not be verified from this environment — there's no way to drive an actual browser here — and are documented in `extension/README.md` as the manual verification the user needs to run.

## ADR-016 — Job Discovery: add Adzuna as a second source, unify dedup across both
**Decision (Phase 7.5):** Adzuna's public search API (`api.adzuna.com/v1/api/jobs/{country}/search/{page}`) is added alongside Greenhouse, not in place of it — Greenhouse stays for "I know this exact company is hiring," Adzuna covers broad keyword-driven discovery, which Phase 7's own retrospective flagged as the missing piece. Both sources live under `lib/discovery/` behind a shared *output* type (`DiscoveredJobRaw`) and a shared dedup-aware insert path (`lib/discovery/insert-jobs.ts`) — not a single `.search()` interface forced onto both, since Greenhouse enumerates one company's board and Adzuna keyword-searches globally; those are genuinely different query shapes and unifying the input signature would be exactly the unnecessary abstraction CLAUDE.md warns against.
**Verified against Adzuna's own docs and ToS before implementing, not assumed from memory:** `app_id`/`app_key`/`what`/`what_exclude`/`where`/`salary_min`/`salary_max`/`results_per_page` and the response shape (`results[]` with `id`, `title`, `company.display_name`, `location.display_name`, `description` — explicitly documented as a snippet, never the full posting — `redirect_url`, `salary_min`/`max`) are all confirmed directly from `developer.adzuna.com/docs/search`. **Not confirmed:** `max_days_old` (recency) — referenced widely in third-party integration guides but absent from Adzuna's own docs page I could reach, and their interactive reference 404'd. It's wired into the request but flagged in code as unconfirmed; the acceptance test for this phase should smoke-test it live before it's trusted for the "posted within" filter.
**No full-text parameter exists** — confirmed by the docs' own wording, not inferred. Every Adzuna result is a snippet with a `redirect_url`; full text comes from running the existing SSRF-guarded `fetchJobPageText` (Job Analyzer's, reused unchanged) against that URL, concurrently across the batch (not sequentially — up to `ADZUNA_RESULTS_PER_PAGE` fetches in one server-action invocation would risk a serverless timeout run sequentially; `fetchJobPageText` already has its own ~10s internal timeout, so `Promise.all` bounds the batch to roughly one fetch's worth of wall-clock instead of the sum). On failure, or on suspiciously short fetched text (under 200 chars), the row keeps Adzuna's snippet and is marked `jobs.is_snippet_only = true` — a plain boolean, not an enum, since there are exactly two states. `app/(dashboard)/jobs/discover/page.tsx` sets `maxDuration = 60` as a safety margin for this batch.
**Dedup unified across both sources, not just added for Adzuna:** `jobs.external_id` (nullable text) plus a new partial unique index on `(user_id, source, external_id)`. Greenhouse's list API already returns a stable numeric `id` per job — previously uncaptured — so it was retrofitted to populate `external_id` too, rather than leaving the two sources on two different dedup mechanisms under one table. The old `source_url`-based partial index from migration 0008 is kept, not dropped: pre-migration Greenhouse rows have no `external_id` yet, so both indexes stay active (a row is rejected on a duplicate `source_url` OR a duplicate `(source, external_id)`) — no backfill migration needed, and the only cost is a narrow, low-consequence edge case (a job discovered under the old scheme and rediscovered post-migration under a changed URL could theoretically duplicate once).
**Filter mapping, stated explicitly per row rather than assumed uniform:** role/location/exclude/salary-min are real Adzuna search parameters, pushed server-side — a materially richer pre-fetch filter set than Greenhouse's board-listing API can ever offer. Experience range has no Adzuna equivalent (job-search APIs don't structure "years required" as a field) — it stays a **post-extraction** filter, reusing the exact `parseMinYears`-based filter already in `DiscoveredJobsList` unchanged, since that filter was already source-agnostic.
**Scoring:** zero changes to `extractJobFields`, `analyzeMatch`, `ProcessJobButton`, or `DiscoveredJobsList`'s scoring logic — all already operate purely on `jobs.id`/`raw_description` with no source-awareness. The only page-level change is the discover query switching from `.eq("source", "greenhouse")` to `.not("source", "is", null)`, so both sources land in one unified "Discovered jobs" list with a per-row source badge, rather than two separate lists.
**Batch size:** `ADZUNA_RESULTS_PER_PAGE = 20`, a plain constant — every result costs up to 2 AI calls once clicked through (extraction + scoring), so 20 is a conservative default against Gemini's free tier, raised later by editing one constant. Adzuna's own free-tier limit (25/min, 250/day per their ToS) isn't the binding constraint — one search is one hit regardless of page size.
**Credentials:** `ADZUNA_APP_ID`/`ADZUNA_APP_KEY` are server-side-only env vars, read only inside `lib/discovery/sources/adzuna.ts`, never `NEXT_PUBLIC_`. Missing either returns a plain `ActionState`-shaped error before any network call, never a crash. `ADZUNA_COUNTRY` defaults to `us`, validated against a known-country allow-list, no per-search picker (single-user).
**Attribution and terms, checked directly against Adzuna's ToS, not assumed:** the full "Jobs by Adzuna" logo-badge requirement is aimed at published/commercial partners; the operative clause for any use is acknowledging Adzuna as the source wherever results are shown. A small "via Adzuna" text link to the original listing is added on Adzuna-sourced job rows — proportionate for a private single-user app; the fuller badge would need revisiting if jobpilot ever became multi-user/public-facing (ADR-007 territory). Separately, the ToS's 14-day trial-storage restriction is explicitly scoped to "commercial, government or academic organisation" use — "personal research" is named as its own permitted category — so ongoing storage of discovered jobs for this single-user tool reads as fine under that clause. That's a reading of the fetched ToS text, not legal advice, and is flagged as such rather than asserted as settled.
**Untrusted-content discipline:** Adzuna's JSON response, the description snippet, and the fetched redirect-page text are all untrusted per ADR-008, flowing into `extractJobFields`'s existing data-only turn exactly like Greenhouse's `content` field and Job Analyzer's pasted text already do. Zero changes to `lib/ai/` — being "an API" changes nothing about the framing.
**Verification note:** request/response shape verified live against the real Adzuna API (with the project's real `app_key` and a placeholder `app_id`) before this ADR was written — confirmed the endpoint accepts the constructed query without a parameter-shape error and returns Adzuna's documented `AUTH_FAIL` response for bad credentials, exactly as the error-handling path expects. Once a real `ADZUNA_APP_ID` was provided, a full live smoke test against `fetchAdzunaJobs`/`upgradeToFullText` (the actual module code, not a reimplementation) confirmed: `max_days_old` is real and works (result counts changed plausibly with/without it — the one parameter this ADR flagged as unconfirmed against Adzuna's own docs); `external_id` values are genuinely unique per page (20/20); and `where` is a strict geographic filter, not a remote/onsite toggle — `where=remote` silently returns zero results because "remote" isn't a place name, confirmed by testing real city names against the same query. The UI's location field was corrected (placeholder + helper text) before this could confuse the user the way it initially confused this verification pass.
**Finding that changes the practical framing of the full-text upgrade — corrected once, see ADR-018 for the correction of the correction:** Adzuna's `redirect_url` comes in (at least) two distinct shapes: `www.adzuna.com/land/ad/{id}?...` returns an unconditional 403 from Adzuna's own CloudFront/bot-protection layer (confirmed with `curl` directly — browser User-Agent, following redirects, retried — so not this app's User-Agent or redirect handling), while `www.adzuna.com/details/{id}?...` fetches fine (`curl` confirms 200). The initial 5-result sample used to write this ADR happened to draw only `/land/ad/` results, which produced the overly pessimistic "almost never succeeds" claim below — corrected in ADR-018 once a larger sample showed the real split is roughly 1-in-4 full text, not near-zero. The fallback path itself was always correct; both the original pessimistic claim and this correction are about the expectation, not the code.

## ADR-017 — Three fixes from the first live pass on Adzuna
**Context:** the user tested the Adzuna flow live and reported three problems in one pass. All three are fixed; none required rethinking the Phase 7.5 architecture.
**1. Discovery is now review-before-save, for both sources.** `fetchDiscoveredJobs` (Greenhouse) and `searchAdzuna` no longer call `insertDiscoveredJobs` themselves — they return the filtered candidate list (`DiscoverState.results`) to the client, rendered by a new `DiscoveryResultsPreview` component with a per-job "Save job" button (`saveDiscoveredJob`, a plain function called via `startTransition`, same shape as Phase 1.5's `commitImport` — its input is a client-held object, not `FormData`). Nothing lands in `jobs` until explicitly saved. **Applied to Greenhouse too, not just Adzuna**, even though the user's complaint was specifically about an Adzuna search: both actions share the same insert path, and leaving Greenhouse auto-inserting while Adzuna required review would be an inconsistent split on the same page for no real reason. This is the same "review before persist" instinct as ADR-010 (resume import) — a broad-net discovery action (especially Adzuna's open keyword search, as opposed to Greenhouse's known-company enumeration) surfaces plenty of irrelevant results, and auto-saving all of them was never actually asked for by Phase 7's acceptance criteria — "search produces a ranked list," not "search populates your tracked jobs."
**2. `analyzeMatch` no longer dead-ends on an unextracted job.** The reported symptom — clicking "Analyze match" and getting "This job hasn't been analyzed yet" — was `analyzeMatch`'s own early-exit for a missing `job_requirements` row, hit whenever a job is viewed without first running the discover page's separate "Extract & score" step (trivial to do by clicking a job's title link instead of its button). This was a **pre-existing gap that predates Adzuna** — it affected Greenhouse-discovered jobs identically — just far more likely to surface once broad Adzuna search made "click a result to look at it" a much more common first action than it was with Greenhouse's narrower per-company flow. Fixed at the root: extraction logic was factored out of `discover/actions.ts` into `lib/jobs/extract-requirements.ts` (`ensureJobRequirements` — idempotent, a no-op if requirements already exist), and `analyzeMatch` now calls it before checking for requirements instead of erroring if they're missing. "Analyze match" is now a true one-click action regardless of navigation path, matching how manually-pasted Job Analyzer jobs already behaved (extraction and the ability to match were never two separate steps there).
**3. Job detail page now links to the original listing.** `jobs.source_url` was already stored for every source (Adzuna, Greenhouse, and manually-pasted-by-URL jobs alike) but was only ever used as a text suffix ("Original description **(from URL)**") on a collapsed raw-text panel — never a clickable link. Also a **pre-existing gap, not Adzuna-specific** — just newly consequential, since Adzuna's snippet-only jobs (see the finding above) don't contain a usable apply link anywhere in their truncated text the way a full Greenhouse posting might. A plain "View original listing" link now appears on the job detail page whenever `source_url` is present. Note: Adzuna's `redirect_url` returning a 403 to this app's own server-side fetch does **not** mean the link is broken for a human — bot protection like this almost always distinguishes on things a real browser click satisfies and a bare server fetch doesn't (cookies, JS execution); this wasn't independently re-verified by clicking it in an actual browser, since nothing in this environment can do that.

## ADR-018 — Correcting ADR-016/017's "almost never succeeds" claim on Adzuna full-text
**Context:** the user flagged a saved Adzuna job (CBRE, "Automation Engineer") whose extracted requirements were nearly empty, and asked how it compared to a fully-extracted LinkedIn-pasted job. Checked the actual row instead of guessing from the screenshot.
**What the CBRE job actually was:** `raw_description` length 500, `is_snippet_only = true`, `source_url` an `adzuna.com/land/ad/...` link. This is exactly the bot-blocked case ADR-016 described — the AI correctly extracted the one responsibility and handful of keywords that were actually present in the 500-character truncated snippet, rather than inventing more. Not a bug; the truth-and-safety rule against fabricating content from nothing was working as intended, just against thin input.
**What was actually wrong: ADR-016/017's characterization of how often this happens.** Querying the full set of saved Adzuna jobs (18 at the time) found **5 with real full text (`is_snippet_only = false`), 13 snippet-only — roughly 1-in-4, not "almost never."** The original claim was written from a 5-result sample that happened to draw only the blocked URL shape. A follow-up check found the actual distinguishing factor: Adzuna's `redirect_url` comes in two shapes, `adzuna.com/land/ad/{id}` (confirmed 403 via direct `curl`, unrelated to this app) and `adzuna.com/details/{id}` (confirmed 200 via direct `curl`) — which shape a given listing gets isn't something this app's request controls; it's decided by Adzuna per-listing (likely based on how that employer's feed is set up), and the code already handles both correctly by attempting the fetch and falling back on failure. No code change was needed here — the existing fallback was always right; only the documented expectation was wrong, and is corrected to "roughly 1-in-4 get full text" rather than "almost never."
**New UI fix, since the real gap was discoverability, not extraction quality:** the job detail page now shows a note directly on the "Extracted requirements" card whenever `job.is_snippet_only` is true, explaining that the description is a truncated snippet (not the full posting) and pointing at the "View original listing" link (ADR-017 #3) to read the real posting. Previously this context only existed on the discover page's pre-save preview list, not on the job's own page after saving — exactly where the user was confused.

## ADR-019 — "Exclude" leaking abbreviations, and a paste-the-full-posting path for snippet-only jobs
**Context:** two more reports from live use. (1) Searching with "exclude: senior" still returned senior-level listings. (2) A saved Adzuna job (Lumen, "Lead Software Developer") had thin requirements while the real posting behind "View original listing" has full responsibilities, skills and experience level — the user wants those extracted.
**1. Exclude now re-checks titles after the Adzuna search, abbreviations included.** The form → zod → `what_exclude` wiring was correct; live-testing Adzuna directly showed its `what_exclude` only drops exact words — `what=software developer` returned 4 senior-ish titles in the first 50, `what_exclude=senior` cut that to 1, and the survivor was "**Sr** Software Development Engineer." `searchAdzuna` now filters the returned titles itself (whole-word match, split on commas/whitespace to mirror Adzuna's word semantics) with a small alias map (senior↔sr, junior↔jr, manager→mgr, principal→prin), on top of — not instead of — the API parameter, so the server-side exclusion still narrows the result pool first. Live-checked: the "Sr …" leak is dropped, "Seniority Analyst" isn't a false positive. A title like "Lead Software Developer" is intentionally *not* excluded by "senior" — guessing that "lead" means "senior" would silently hide jobs the user didn't ask to hide.
**2. Snippet-only jobs get a "paste the full posting" action instead of a smarter fetch.** The Lumen job's `source_url` is the `land/ad` shape that returns 403 to server-side fetches (ADR-018). Getting past that would mean defeating Adzuna's bot protection — not on the table. The honest route is the one the user already demonstrated works: the human copies the posting from their browser. The job detail page now shows an "Add the full posting" card whenever `is_snippet_only` is true; `replaceJobDescription` validates the pasted text (200–50,000 chars), overwrites `raw_description`, sets `is_snippet_only = false`, deletes the old `job_requirements` and `job_scores` (the score was computed against thin requirements, so keeping it would be misleading), then re-runs the existing `ensureJobRequirements` — no new extraction path, no second scoring mechanism. Seniority benefits too: `scoreSeniority` reads `experience_requirement`, which a 500-char snippet rarely contains. Pasted text is treated as untrusted input by the same extraction prompt as every other job description. Resume versions already generated for the job are left alone — they're user artifacts, not derived cache.
**Not verified:** the paste flow through the logged-in UI — nothing in this environment holds an authenticated session. Typecheck, lint and production build pass; it reuses `ensureJobRequirements`, which is already exercised live by `analyzeMatch`.

## ADR-020 — Zero-click full-posting capture via the browser extension (amends ADR-015)
**Context:** the paste flow (ADR-019 #2) produced exactly the extraction the user wanted on the Lumen job, but they asked for it to be automatic — no navigate/copy/paste. Re-checked the server-side route first: for that job, *both* Adzuna URL shapes (`/land/ad/{id}` and `/details/{id}`) return 403 to a plain request, so there is no server-fetchable page to fall back to; getting past it would mean defeating bot protection, which stays off the table. The user's own browser is the only legitimate reader of those pages, and the Phase 8 extension already runs there. Offered zero-click vs. one-click-from-the-popup; the user chose zero-click.
**How it works:** the extension's background worker watches for tabs opened *from* a JobPilot `/jobs/{id}` page (`webNavigation.onCreatedNavigationTarget`, with `tabs.onCreated` + `openerTabId` as a fallback), on the known JobPilot origins only. It arms capture only if that job is `is_snippet_only` under the signed-in user's RLS (signed out ⇒ no row ⇒ nothing happens). It then polls the new tab's text (preferring `main`/`article`, falling back to `body`) until it has at least 800 chars and has stopped changing — employer ATS pages like Workday render client-side — giving Adzuna's own redirect page 15s to hand off before settling for it, and giving up after 60s or if the tab closes. It writes the text over `raw_description` with `is_snippet_only = false` **only where the job is still snippet-only** (so a pasted or already-captured description is never overwritten), deletes the job's stale `job_requirements`/`job_scores`, and sends the JobPilot tab back to `/jobs/{id}?captured=1`. That page runs the existing `extractJobRequirements` → `ensureJobRequirements` on load, because the AI provider is server-side only — the extension never calls Gemini or holds its key.
**What this changes in ADR-015, deliberately:** (1) the extension is no longer read-only — it can update `jobs` and delete `job_requirements`/`job_scores`, all still through the user's own RLS policies, with no new API route; (2) permissions widen from `activeTab` + the Supabase host to `webNavigation` + `<all_urls>`, since a listing can redirect to any employer domain and there's no user gesture on that tab for `activeTab` to piggyback on. Reading is still gated on "this tab was opened from one of your snippet-only JobPilot jobs." The "never submits anything" guarantee is unchanged — capture only reads text. Captured page text is untrusted input, handled by the same extraction prompt as pasted text (ADR-008). The paste box stays as the fallback for when the extension isn't installed or capture fails.
**Not verified:** none of the browser-side behavior — whether `onCreatedNavigationTarget` fires for the `rel="noopener"` "View original listing" link (the `openerTabId` fallback is there in case it doesn't), the timing against real Workday/Adzuna pages, or the reload-and-extract hand-off. Nothing in this environment can drive a real signed-in Chrome. Extension typecheck and build pass and the built manifest carries the new permissions; app typecheck, lint and production build pass.

## ADR-021 — Declined: automated LinkedIn scraping (any account); built a CSV import instead
**Request:** the user supplied `jobs.csv` — 50 rows exported from their own LinkedIn job search, every `url` a `linkedin.com/jobs/view/...` link — and asked for a headless test that fetches those URLs server-side to pull requirements, first for personal use, then on a "guest account" when personal use was raised as a concern.
**Declined, and held on the second ask.** ADR-009 already rules this out: LinkedIn's terms of service prohibit automated scraping, and that prohibition doesn't have a personal-use or a which-account exception — an automated request against LinkedIn's servers is the same ToS violation regardless of who owns the account making it, and running it from a throwaway account is more consistent with evading consequences than with it being permitted. No script was written or run against these URLs, including as a one-off test.
**Built instead: a CSV import, with zero fetching of any kind.** `parseJobsCsv` (`lib/jobs/parse-jobs-csv.ts`, a small hand-written RFC4180-ish parser — no new dependency for a one-off personal feature) reads `title`/`company`/`location`/`url` columns; `importJobsCsv` inserts one job per row with `source_url` set, `raw_description` a fixed placeholder, `is_snippet_only = true`, `source = null` (same as any manually-entered job — not folded into the Adzuna/Greenhouse `JobSource` type, since a curated personal list isn't a third discovery source under Phase 7.5's scope). Dedup reuses the existing `(user_id, source_url)` unique index from Phase 7 — re-importing the same CSV adds nothing twice. A new "Import a CSV" card on the discover page uploads the file directly (no paste step, matching the "headless" framing of the ask, since bulk-inserting rows the user already curated themselves isn't the kind of broad-sweep result set ADR-017 was guarding against).
**Getting an actual description into each row is unchanged from ADR-019/020** — the paste box or the browser extension's own-browser capture, since both already work for any snippet-only job regardless of how it was created. Verified live: the parser against the real `jobs.csv` (50/50 rows, quoted-comma titles handled correctly); typecheck, lint, and production build all pass. Not verified: the import form through the logged-in UI (no authenticated session available here) and the extension capture against a real LinkedIn tab (unchanged limitation from ADR-020). `jobs.csv` itself is gitignored — it's the user's personal job-search data, not project source.
